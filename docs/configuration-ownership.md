# Configuration ownership and consolidation

Status: steps 1 through 6 and the backend logging batch are committed.
Activation routes share candidate construction and
reject host changes that the current runtime cannot apply. New activations
separate host settings from plugin inputs, and runtime projections use pinned
bindings. Settings has one host editor; the old named Application Profile editor
and file overlay are removed.
Playback speed and the reviewed unused settings are also removed. Real-time
worker logging remains deferred. The current instruction authorizes completing
and committing the remaining steps after validation.

The inventory covers all 38 leaf keys currently declared in
[`settings.toml`](../omnibci/conf/settings.toml), all ten bundled plugin schemas,
and the additional configuration inputs identified below. Key names in the
tables are existing names, not a proposal to rename every setting.

## Ownership rules

| Configuration | Authoritative source | Single editing location | Application |
| --- | --- | --- | --- |
| Plugin parameters | A named Plugin Profile for an exact contribution and version | Setup, under that plugin | Save preserves the running values; Review and Apply selects a pinned copy |
| Acquisition montage | Acquisition Plugin Profile: read-only `acquisition_montage` observation and editable `manual_montage` for missing facts | Setup / Acquisition / Source montage | Read from the applied source; Save and Review/Apply manual declarations |
| Plugin selection and filter order | Activation bindings | Setup, plugin/profile selectors and filter chain | Review and Apply |
| Shared runtime settings | Host settings, copied into the candidate activation | Settings / General, grouped by subsystem | Review and Apply at a supported runtime boundary |
| Channel binding and software reference | Decoder Plugin Profile `processing_input`, pinned in its activation binding | Setup / Signal Processing / Decoder / Processing input | Profile Review and Apply; input changes rebuild and prepare processing before streaming |
| Backend startup settings | Host settings or explicit deployment inputs | Settings / General for supported local settings; deployment configuration for environment inputs | Backend restart; never report an engine rebuild as sufficient |
| Runtime context and state | Derived from accepted/applied configuration and runtime state | Read-only | Generated by the host |

The [minimum montage implementation](montage-implementation-plan.md) stores
source facts in Acquisition and algorithm input choices in each decoder profile.
Observed device metadata remains read-only and is persisted without its connection
ID. Manual declarations fill absent facts and cannot override reported values.
They are pinned in the acquisition binding; refreshing an observation does not
silently change accepted runtime inputs. Decoder profiles independently retain
ordered outputs, exclusions, and original/single/average/bipolar software reference.
Saving either profile does not change a running experiment.

The binding editor shows Acquisition channels on the left and ordered algorithm
inputs on the right. A string output such as `"Oz"` selects the same-named source;
`{"name": "Oz", "source": "CH1"}` explicitly binds a differently named source.
Targets and selected sources are unique. Empty `outputs` retains dynamic selection
of all non-excluded source channels; it never means an empty input. Explicit
bindings retain their names and order when the Acquisition changes, and missing
sources must be resolved before preparation. References and exclusions identify
Acquisition source names. Aliases do not change Acquisition metadata or infer an
electrode position from an algorithm input name.

At runtime the bound, reordered and re-referenced signal enters Epoching
first, including trigger detection and pre-trigger buffering. The post-trigger
window accumulated up to each decode call passes through the ordered optional
Filters and finally the Decoder; it need not extend to an end marker. Neither
pre-trigger data nor the trigger row enters the decoder window. The separate
`latest_samples` input contains only the most recently appended epoch segment;
it is mapped and re-referenced but not epoch-filtered. Pipeline callers must
supply it explicitly, using `(signal_channels, 0)` when no new segment is
available. It is not all samples received since the previous decode and never
defaults to the full window. See the [input contract](decoder-plugin-development.md#python-contract)
for readiness, state and boundary behavior.
The profile's storage owner does not imply a direct Acquisition-to-Decoder route.

Decoder contributions own read-only `channel_requirements` in their manifests.
The host checks signal type, minimum count and required names against the mapped
decoder input, excluding trigger and reference-only dependencies. `default_names`
initializes new profile inputs only; it never replaces a saved selection. These
requirements travel through the plugin catalog, not through a duplicate profile
parameter. The [Decoder developer guide](decoder-plugin-development.md) describes
the fields and provides the starter displayed in Extensions.

Signal Processing automatically uses the currently selected Acquisition binding. Decoder
profiles store no fixed Acquisition profile identity.
The pinned decoder `processing_input` is consumed directly with Acquisition's
`SourceMetadata`; runtime materialization does not generate `SIGNAL.setup` for
these profiles. Existing profiles and activations without `processing_input`
retain their legacy behavior and revision hashes. Old `SIGNAL.setup` and
`ACQUISITION.channel_names` are read-only compatibility inputs; the global signal
writer and `include_signal_setup` review switch have been removed. Adopting a
profile input requires an explicit save and
review. Legacy source declarations must first be completed in Acquisition; they
are not silently copied into a decoder profile or discarded by a parameter edit.
Changes to channel meaning require a stopped-stream rebuild and new preparation.

If a decoder declares channel requirements, a historical profile with neither
an input nor a legacy setup receives a transient identity input in its runtime
projection. This retains all source channels and the original reference while
requiring real metadata and preparation before streaming. It does not use plugin
default suggestions or rewrite the saved profile, activation, or revision.

`GET /api/v1/config/signal` reports `source_binding`, an opaque `source_revision`,
and the pinned `processing_input`, `accepted_input`, and `active_input`. Saved
decoder drafts remain in the profile editor until Review and Apply. The read API
retains its legacy setup views for compatibility. Preview submits a draft input
and may include `expected_source_revision` and the exact `decoder_selection`
being edited. Preview checks that decoder's requirements independently of the
currently selected decoder; the server resolves Acquisition-owned
metadata and rejects caller-supplied metadata overrides or a stale source revision.

Connected metadata is cached under the acquisition profile, plugin selection,
parameters, and manual montage that own the source. Another source profile cannot
reuse that cache, even when it selects the same plugin. Disconnect invalidates
the cache and readiness; reconnection requires current metadata and a new receipt.
Offline views can use matching profile observations and pinned manual declarations,
marked with `metadata_origin: profile`; they do not grant streaming readiness.
Conflicting facts keep the source binding visible with `source_error`, while
preview and preparation remain blocked until the conflict is resolved.

| Unused or unsupported legacy settings | No new editable owner | No replacement editor | Remove only in a reviewed implementation step |

These locations describe the target interface. Currently most host settings are
not exposed through the configuration API. This inventory does not authorize
adding controls for every key.

Each parameter has one writable owner. Activation retains independent copies of
accepted values so that a saved Profile edit cannot mutate a running experiment.
Such copies are intentional; independently editable copies of the same parameter
in host settings are not.

Schema `x-scope` distinguishes portable and machine-specific plugin values. A
device address remains a plugin parameter even when it is machine-specific.
No accounts, synchronization service, new extension interface, or montage work
is needed for this consolidation.

behavior, not a promise that every `x-apply: module` edit restarts only one
process. Acquisition changes currently rebuild the engine graph. A running
rebuild uses a continuation session; decoder/filter trial-boundary changes

Important boundaries:

- Source sampling information is owned by Acquisition. Signal Processing receives it as
  context; a decoder must not expose a second independently editable sample rate.
- Scan45 channel count includes the final event channel. This review does not
  change that convention or add channel-layout/montage configuration.
- Curry8 and File Reader obtain actual data dimensions from the device/file,
  while the Profile's sampling declarations still feed processing and status.
  The current implementation does not consistently validate that they agree.
  Preserve Acquisition ownership; handle metadata consistency in a separate
  reviewed fix, without silently deleting declarations or changing their values.
- CCA initialization currently reads `ssvep.duration` and `ssvep.offset_time`;
  FBCCA reads the corresponding `ALGORITHM` keys. Preserve existing accepted
  Profile values; do not silently choose a different legacy value during cleanup.
- `ALGORITHM.baseline_duration` is deliberately absent from this table. It
  controls framework pre-trigger buffering, not a decoder or filter constructor.
- `ACQUISITION.file_reader_play_speed` has been removed from the default file,
  configuration editor/API whitelist, and File Reader implementation. The read
  loop is unchanged. Do not add a nonfunctional Profile field.

The console labels `ALGORITHM.baseline_duration` as **Pre-trigger duration (s)**;
the stored key remains compatible. It retains up to the configured number of
samples immediately before each start marker, including the tail of a previous
trial when present. Capture is independent of baseline correction. The
`BaselineCorrection` filter uses the entire retained segment as its reference
interval and subtracts its per-channel mean from the window.

The host runtime section of a future activation must contain only settings used
by that runtime. Startup-only and deployment inputs must not trigger a runtime
rebuild or be reported as applied when their consumers have not been recreated.

### Step 2: one configuration editor per owner

Settings / General retains console preferences and the two previously editable
host parameters, `ALGORITHM.baseline_duration` and `NEUROENGINE.queue_size`.
Other host parameters are not newly exposed. Plugin selection and parameters
are edited through Setup / Plugin Profiles. Advanced and all named Application
Profile controls have been removed.

`GET /api/v1/config` returns `entries` with a saved `value`, not a claim about
the currently running value. Step 5 adds a saved `revision` to this response.
`PATCH /api/v1/config` accepts `updates` and the required `expected_revision`, and
returns `saved` keys, the new `revision`, and `engine_restart_required`. Plugin keys and mixed
host/plugin writes are rejected before mutation. Removed `scope` and
`description` fields are rejected; `/api/v1/config/profiles` routes no longer
exist. Plugin Profile APIs and accepted activation remain separate and intact.

Saving host settings does not apply them. Review retains the existing plugin
bindings (`refresh_slots: []`) and includes the saved host settings in the
candidate. Configuration apply and host persistence remain mutually exclusive.

`OmniBCISettings` now reads the settings file or an installed worker snapshot;
it never reads the old `conf/profiles/` directory. Existing accepted values and
revisions are preserved. Fresh initialization uses the flat defaults still
present in `settings.toml`. Step 3 removes those inputs from new activation host
settings; refining host candidate merging remains step 4. Retired files are not
deleted or migrated.
The former Review incorrectly listed `CONFIG.initialization_warnings` as a
changed host field alongside a real edit. Step 4 keeps these accepted diagnostics
read-only and excludes them from runtime materialization.

An existing Application Profile can contain values different from the raw
settings file. Those values must be reviewed before choosing the saved host
values for the next Apply. In this workspace, the old profile contains queue
capacity 90 while the raw settings file contains 100; that value decision is
separate from removing the editor and does not rewrite the accepted activation.

### Step 3: plugin inputs belong to pinned bindings

New activations omit the 19 flat plugin selection and parameter keys listed in
sections 1 and 2 from host settings. They retain host-owned values such as
`ALGORITHM.baseline_duration`, optional `ACQUISITION.channel_names`, and output
deployment settings. Plugin parameters remain in their selected bindings;
Profile edits cannot change the pinned values until explicitly refreshed.

Existing accepted activations are read without changing their stored contents,
revision, or Profile files. Their old flat plugin copies remain inert historical
metadata: a new proposal retains those exact old copies, so editing an unused
raw plugin key cannot change the candidate revision or request a rebuild. New
host input cannot introduce or update these copies. Runtime materialization
always removes them before projecting values from the pinned bindings.

Runtime projections retain the existing plugin aliases, ordered filter aliases,
and source parameters under `ACQUISITION.*`. The source's sampling declaration
therefore reaches both the engine and `PluginContext`. Decoder and trigger
parameters are supplied directly from bindings; no second flat parameter copy
is generated for them. This preserves existing trial-boundary decoder updates
and output-module changes. Revision and serialized bindings remain generated
runtime fields.

The selected source must provide positive integer `sample_rate` and
`channel_number` values in its resolved Profile. Missing or invalid declarations
fail explicitly before runtime projection instead of falling back to old host
copies or the engine's default sample rate. An existing third-party source that
only stored these values in host settings requires a reviewed Profile/schema
correction; its accepted file is not automatically rewritten. Device/file
metadata consistency after connection remains a separate issue.

The raw `settings.toml` plugin entries remain explicit first-initialization
inputs for this step; they are not live controls. Their existing values are
copied into initial Plugin Profiles before filtering the activation host
settings. This does not replace values with schema defaults, select another
plugin, or rewrite actual configuration files. Retiring this initialization
source requires a separate explicit first-initialization policy. Step 6 removes
standalone runtime fallback; this explicit initializer remains. The
startup-only/diagnostic change rules are covered by step 4.

The plugin exclusion set covers the 19 reviewed flat keys, not arbitrary
third-party legacy prefixes. Unknown legacy seed fields can still remain in
host settings until that initialization path is retired; step 4 rejects changes
to such unclassified fields. Plugin Profile parameters themselves remain
governed by each plugin's full schema, without a fixed parameter list.

### Step 4: one candidate construction policy

`PUT /api/v1/config/activation` and `POST /api/v1/config/apply-plan` share the same
`include_host_settings` and `refresh_slots` inputs. Host refresh defaults to
`false` on both routes. Plugin selection therefore retains accepted host values
unless a caller explicitly includes saved host settings. General uses
`include_host_settings: true` and `refresh_slots: []`; the plugin editor retains
its explicit slot refresh behavior. Direct activation remains idle-only, while
Review/Apply retains its pinned plan and runtime acknowledgement requirements.

The shared configuration service reads the selected host source once when
constructing a candidate. Its runtime host key set is the 15 existing inputs
listed in sections 3 and 5, including `ACQUISITION.channel_names` and
`NEUROENGINE.startup_timeout_s`. Existing `ACTUATION.enabled` and both
`auto_spawn` settings remain runtime topology/deployment inputs. They still
require the current managed-process and external-peer checks.

The backend-startup boundary covers `NEUROENGINE.command_timeout_s`,
`PERSISTENCE.session_repository`, `PLUGINS.user_dir`, `LOGGING.level`, and
`LOGGING.file_path`. The service captures the loaded startup values when the
backend is assembled, using the existing defaults for absent keys. Plugin path
comparison uses the effective resolved path, including `OMNIBCI_PLUGIN_DIR`
precedence. It does not compare against potentially stale startup copies in an
accepted activation.

If an explicit host refresh finds a changed startup input, both routes return a
validation error naming the keys and requiring a backend restart. No plan or
activation is published, even if the engine is stopped or the request also
contains valid runtime changes. The existing console request-error display
shows the reason. Restoring the loaded value or restarting the backend clears
that condition; restarting only the engine does not. This adds no startup
settings editor, file watcher, or new restart operation.

Generated fields, diagnostics, retired settings, old plugin copies, and old
startup copies are inert in candidate construction. Existing accepted copies
retain their exact values; new host input cannot edit them or force a different
revision. Runtime materialization excludes them and generates revision/binding
fields afresh. The initializer still stores its own generated warnings as
read-only metadata, so diagnostics remain available after restart.

First initialization may retain unknown fields from its explicit settings seed;
existing accepted unknown values are also preserved. Adding, changing, or
removing an unknown field through a later host refresh is rejected rather than
silently ignored or reported as applied. Such a field needs a reviewed host
owner or must become a Plugin Profile parameter. This does not restrict the
plugin's own schema or rewrite actual saved data.

Normal engine shutdown no longer treats its retained historical Actuation
snapshot as an active output. Failed shutdown or other retained graph ownership
still prevents an idle selection from being accepted over unconfirmed runtime
resources. Running output availability and external-peer restrictions remain
enforced before any pause, rebuild, or persistence.

### Step 5: user host settings and optimistic saves

The packaged `omnibci/conf/settings.toml` is a read-only defaults source. Saved
host overrides live in `settings.toml` alongside `activation.toml` and
`plugin-profiles/` in the shared user configuration directory:

| Platform | Default directory |
| --- | --- |
| macOS | `~/Library/Application Support/OmniBCI` |
| Linux | `$XDG_CONFIG_HOME/OmniBCI`, normally `~/.config/OmniBCI` |
| Windows | `%LOCALAPPDATA%/OmniBCI` |

`OMNIBCI_CONFIG_DIR` remains an absolute deployment override. A missing user
settings file uses the packaged defaults without copying them. A save writes
only the user overrides, preserving their TOML comments. The user file accepts
the existing runtime and backend-startup host keys; plugin values, generated
fields, retired profile metadata, and unknown keys fail clearly. A corrupt file
is never silently replaced. Pointing the user file at the defaults file is
rejected. No existing Profile, activation, or retired file is migrated.

GET returns the saved values and a SHA-256 revision from the same read. PATCH
requires that revision and returns the committed revision. The token includes
the defaults bytes, user file bytes, and presence of the user file, so manual
edits, deletion, and changes to defaults invalidate stale edits. This is a host
storage revision, independent of the BCI activation revision. A conflict returns
409; the console retains its draft and requires an explicit refresh. There is
no automatic overwrite or retry. Invalid input returns 422; inaccessible
storage returns 503. Queue capacity must be positive; pre-trigger duration must be
finite and nonnegative.

Host writes use a process lock (`flock` on POSIX, `msvcrt.locking` on Windows),
then compare the current revision and replace the document through a flushed,
fsynced temporary file in the same directory. A failed write leaves the previous
saved file and committed in-memory values intact. These guarantees cover
cooperating API writers; an external editor does not participate in the lock.
The existing engine transition guard still excludes Save during Apply.

Backend assembly and host Review read saved values at their management
boundaries. Saving does not change accepted or running configuration; backend
startup checks from step 4 remain in effect. Logging, container assembly, and
the loaded startup baseline share one captured host snapshot. An edit during
startup therefore cannot be mistaken for a value the backend already loaded.
Worker `get()` and `snapshot()` read
only their injected dictionary, without file access or added locking. Importing
the global settings adapter does not read the user file. Explicit complete-file
adapters remain available for isolated tests and embedding.

### Step 6: explicit configuration at every launch

Backend engine startup uses the accepted-configuration resolver. It
reads `activation.toml`, validates its pinned selections and resolved parameters,
and materializes one runtime snapshot. It neither refreshes saved Profiles nor
creates an activation. Missing, corrupt, unavailable, or unsupported selections
fail before runtime construction. Standalone scripts now obtain a projection
from the backend as described below.

The standalone scripts install that snapshot in the in-memory settings adapter
and pass it to the application. Transport addresses and plugins therefore use
the same accepted inputs. Managed subprocess entry points likewise require a
snapshot and no longer mutate raw alias keys. `NeuroEngineBuilder` also requires
an explicit snapshot; its host controls are derived from that snapshot unless a
caller supplies an explicit builder configuration.

Runtime plugin loading requires `PLUGINS.bindings`. It resolves the exact
package/contribution/version and checks the schema version, with no alias
fallback. Ordered filters come from their binding slots. File Reader, Scan45,
Curry8, and Scan45 Trigger require explicit parameters; CCA and FBCCA also
require sampling context. Their constructors no longer read global settings.
Stateless constructor API 1 contributions can still be loaded through an exact
binding; configurable contributions require constructor API 2. The explicit
first-initialization alias mapper remains separate from runtime loading.

### Independent nodes: role-scoped startup and reconnect

`GET /api/v1/config/nodes/{role}` publishes configuration for external
`stimulation` and `actuation` nodes. While idle it reports `selected` with no
generation; while running it projects the actual applied snapshot. Startup,
shutdown, configuration transition, and recovery states reject publication.
Publication never treats a historical stopped snapshot or saved Profile edits
as current runtime inputs. Backend-managed roles and disabled Actuation reject
external node requests.

The versioned `NodeConfiguration` envelope contains a role, the parent Activation
revision, engine generation, necessary host/context settings, and owned bindings:

| Role | Locally validated and loaded contributions |
| --- | --- |
| Engine | Acquisition, Decoder, Epoch boundary detector, Filters |
| Stimulation | Paradigm, Trigger |
| Actuation | Effector |

Sampling rate, channel count, and optional channel names provide shared context;
other roles' plugin parameters and local paths are omitted. Nodes validate exact
package/contribution/version, resolved defaults, schema version, and local
platform support. They derive aliases from the local catalog. The backend still
needs the complete manifest/schema catalog for configuration authoring, but does
not require remote output plugins to support its operating system.

Standalone scripts use `--backend` or `OMNIBCI_BACKEND_URL`; no local Activation
fallback exists. HTTP fetching and validation happen only between application
lifetimes. Offline, selected, and transitioning backends are retried before
hardware initialization. After local setup, external IPC connections must match
role, revision, and generation through `PeerHello` / `PeerAccepted`; mismatches
cannot route business events or count as connected. Managed subprocesses retain
their existing `StartupReporter` barrier. Each external role has one connection
owner. This handshake confirms configuration consistency, not authentication.

Connection loss stops queued command execution and triggers teardown before
re-fetching and rebuilding. Stimulation clears its initialized trigger after
rendering exits. Actuation requires `Effector.quiesce()` to confirm outputs have
finished or been cancelled before releasing the device. Setup, quiescence,
trigger-clear, and teardown failures stop the script. An explicit normal
application stop does not restart it. No cloud, account, plugin installation,
or cross-node live-apply protocol is added. Revision-changing Apply operations,
including decoder-only changes, are rejected while external roles are configured
on a running engine. Stop, apply, and start the engine to let waiting nodes fetch
the new generation automatically. The API backend and IPC addresses must be
reachable; use explicit backend LAN addresses, not wildcard listener addresses,
for cross-machine IPC.

All configuration reads and validation happen at startup or management/apply
boundaries. Acquisition, processing, trial, rendering, and command timing loops
retain their existing execution model.

### Backend logging: first implementation batch

`LOGGING.level` and `LOGGING.file_path` are host settings read from
`settings.toml` when the API server starts. They are not plugin parameters or
live controls. Supported levels are `DEBUG`, `INFO`, `WARNING`, `ERROR`, and
`CRITICAL`; the default is `INFO`. Editing either key takes effect after a backend
restart, not an engine restart. No new web editor is introduced in this batch.

New activations omit `LOGGING.*`. Previously accepted snapshots retain their
original logging values as inert metadata so their hashes remain valid.
Materialization excludes all logging keys from worker settings. A logging-only
edit therefore never changes the BCI revision or requests an engine rebuild.
Step 4 rejects explicit host Review while saved logging values differ from the
loaded backend values, naming the required backend restart without publishing
an apply plan.

#### Files and ownership

- Relative paths resolve under `platformdirs.user_log_path("OmniBCI",
  appauthor=False)`, the operating system's user-writable log directory. The
  default configured filename is `omnibci.log`; `../` paths escaping this
  directory are rejected. Absolute paths are supported.
- The actual filename includes the backend role and PID, for example
  `omnibci-backend-12345.log`. Each file rotates at 5 MiB with three backups.
  This limit is per process filename; old PID files are not automatically pruned.
- The application installs one owned file-queue handler on the `omnibci` logger. Existing
  handlers, propagation, and root/Uvicorn logging configuration remain intact.
  When no handler is reachable at startup, the existing `logging.lastResort`
  warning output is temporarily forwarded and removed on shutdown. Records that
  already reach another handler do not receive this fallback. The configured
  level applies to the `omnibci` logger and the file sink, including records from
  child loggers with explicit levels. Root/third-party messages are outside this
  file sink.
- Invalid configuration or a destination that cannot be opened fails startup
  explicitly. Importing modules does not open files or start a writer.

#### Queue and lifecycle

The producer shallow-copies each enabled record and calls `put_nowait()` on a
bounded, process-local queue (1,024 records). A daemon thread formats, writes,
and rotates files. Queue overflow drops the new record. Overflow and write errors
increment counters without recursively logging or writing synchronously to
stderr. Existing external handlers may still format/write synchronously; the
application does not replace them. Callers should use lazy logging arguments
instead of eagerly building expensive strings.

Logging encloses container construction and service teardown, with logger cleanup
on exceptional exits. Shutdown detaches the owned handler, restores the
previous logger level, and waits up to one second to drain. If a file operation
remains blocked, shutdown returns with the daemon still alive; undrained records
can be lost on process exit. The consumer closes its own file when it finishes.
Global `logging.shutdown()` does not flush or close the file while the writer
still owns it; it also cannot wait on this sink's file I/O lock.
`app.state.backend_logging` exposes `file_path`, `is_running`, `dropped_records`,
and `write_errors` for diagnostics; this batch adds no public diagnostic endpoint.

Only the backend process enables this sink. Acquisition, processing, stimulation,
Actuation, and standalone entry points are unchanged. Queue operations still
consume CPU and briefly synchronize, so this is not a claim of zero real-time
overhead. Before enabling file logging in real-time workers, measure latency
under normal and saturated logging load, verify hardware timing, and retain
separate process queues/files without reusing BCI event or command queues.

## 5. Additional inputs and derived values

These are outside the 38-key file inventory but must have an explicit boundary.

| Input | Owner and treatment |
| --- | --- |
| `NEUROENGINE.startup_timeout_s` | Existing host runtime input, absent from the file; engine rebuild. Consolidate declared and fallback defaults before exposing it |
| `ACQUISITION.channel_names` | Currently an optional flat input passed into `PluginContext`; no bundled source schema declares it. Keep the current optional context behavior in this batch, add no editor, and review its source contract with future channel-layout work |
| `PLUGINS.bindings` | Derived serialization of accepted bindings; never an editable host setting |
| `CONFIG.revision`, `CONFIG.generation` | Generated accepted revision and process generation; never user-entered settings |
| `CONFIG.initialization_warnings` | Initialization diagnostics; read-only metadata. Exclude diagnostics from future runtime change detection |
| `OMNIBCI_CONFIG_DIR`, `OMNIBCI_PLUGIN_DIR` | Machine deployment inputs; retain explicit path overrides and platform defaults |
| `OMNIBCI_MARKET_URL`, `OMNIBCI_MARKET_REPOSITORY_ID`, `OMNIBCI_MARKET_TRUSTED_KEYS`, `OMNIBCI_MARKET_CACHE_DIR` | Existing market deployment inputs; outside plugin parameters and activation |
| HTTP listener host/port | Server launch inputs, currently supplied to Uvicorn; not a device or plugin Profile |
| Trial count and target cue (`n_trials`, `trial_params`) | Per-command Run inputs; not automatically persisted as Profile configuration |
| Paradigm manifest `params` and packaged stimulus resources | Package-owned metadata/assets; no new editable settings are introduced |

Existing in-memory `settings.use_snapshot()` adapters may remain while consumers
are updated. In a managed worker these read the injected snapshot, so importing
`settings` alone is not evidence of reading an independent disk configuration.
Standalone startup now resolves an explicit accepted configuration;
it cannot silently select a different legacy alias.

Preserve valid current Plugin Profiles and accepted activations where their
